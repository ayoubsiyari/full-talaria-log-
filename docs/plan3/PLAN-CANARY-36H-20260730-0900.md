## BLOCK 3 — 19:00 to 03:00 — THE REPRESENTATION CHANGE, IN TWO INDEPENDENT LANDINGS

### The gate, and it comes first

**No storage changes until the differential oracle exists and has been shown to go
RED on a deliberate corruption.** GATE-01 applies in full: acceptance is demonstrated
failure first, passing second.

The oracle computes, both ways, and asserts **bit-identical**:

- every bar's open, high, low, close, volume and timestamp
- every indicator output series
- every order fill price, stop and target trigger evaluation
- realised and unrealised PnL, and every journal-written value
- session/daily/weekly bucketing boundaries

Then it is proven to work by corrupting one value in the new path by one tick and
watching the oracle fail. An oracle that has never failed is decoration.

### Landing 1 — the accessor boundary. No behaviour change at all.

The risk in this refactor is not the typed arrays. It is that bar fields are read
directly in hundreds of places. So the first landing is mechanical and behaviour-free:
route every bar read through a small accessor API, storage unchanged, and prove
byte-identical output on the oracle. This lands, ships and soaks **on its own**.

A change that alters nothing is the cheapest thing in the world to verify, and it is
what makes Landing 2 a small diff instead of a large one.

### Landing 2 — swap the storage behind the boundary.

Columnar `Float64Array` behind the accessors, behind
`__TALARIA_DISABLE_COLUMNAR_BAR_STORE_V1`, old path intact and reachable by flag
flip without a reload (FLAG-02). Read path first. Write path only once the read path
has soaked.

**Stop conditions — any one of these and Landing 2 is reverted by flag, not
debated:** the oracle fails on any cell; PO sees any wrong value anywhere; the soak
shows a new error class; or the measured saving is under 25%, in which case the risk
is not paying for itself.

## ADDENDUM 09:15 — C's W86 lands and it changes Block 1

Written before the dispatches go out, because two of my own claims are now wrong and
the plan is better for it.

### WITHDRAWN — the 4x gauge blindness

I told the PO his console had been reading roughly a quarter of the truth. **That is
withdrawn.** C sampled `performance.memory.usedJSHeapSize` and the CDP metric that
Performance Monitor actually displays **at the same instant**, nine samples, two arms:
CDP reads `0.695` of `performance.memory`. The console gauge reads **higher**, not 4x
lower, and the sign of my claim was inverted. Corroborated independently: ballast
allocated inside panel A's realm moved the host console reading by +18 MB, which a
main-frame-only counter cannot do.

My error was methodological and it is the one I keep making — I compared a
Performance Monitor reading from one session against console readings from a
different session and called the difference a property of the instrument. Same-instant
or it is not a comparison.

**Two consequences.** First, the 789 MB is still unexplained; C's leading candidate is
a **multi-process split** — `performance.memory` is per-isolate, our four panels share
one renderer, but a 15-pair session is ~30 frames and Chrome may have placed some in
additional renderer processes. Second, and it cuts against us: the PO measured all
night with DevTools open, which **inflates**, so ~12 MB/cycle is an **upper** bound on
the product rate, not an under-read.

**`measureUserAgentSpecificMemory` is cancelled**, and C is right to refuse it. It is
unavailable without cross-origin isolation, and COEP `require-corp` would break
host-to-panel `frame.contentWindow` access — which both the product and the harness
depend on. Turning it on to measure memory would break the feature being measured.

### CONFIRMED, AND IT IS THE LEAK — the document staircase

I earlier recorded the staircase as a misreading. C reproduces it in a controlled
harness on the deployed build, four-up, four cycles: documents **2 → 3, 5, 7, 10**.
Nodes 6226 → 21527. Listeners 1349 → 1887. Peak documents climb too, so retained
documents are still being counted at the next peak. **~2 documents retained per cycle
at ~12 MB each, against a measured floor delta of 24.39 MB/cycle.** The retained
documents account for essentially the whole per-cycle growth.

This closes the attribution. The leak is retained panel realms, exactly where C's
REALM-SURVIVAL work pointed, and the per-cycle growth is now explained rather than
hunted.

**And it gives us the thing we have not had all week: a cheap RED gate on the real
defect.** `DOM-COUNTER-STAIRCASE-V1` is blocking, RED in both arms, one metrics call
per sample, and it runs in about a minute. GATE-01 is satisfied by construction — it
is red on the live defect, not on a synthetic reversal.

**This becomes the loop for the memory kill.** A cuts a retainer, runs the counter,
and knows inside a minute whether documents return to baseline. No snapshot grading,
no overnight wait. C's own note says it better than I would: cheap counters first,
snapshots only for attribution once a counter says there is something to attribute.

Caveat kept in view: the counter cannot separate product-held from inspector-held
documents (4 product vs 8 console at W81), so it is an upper bound. The gate is for
**direction and iteration speed**; REALM-SURVIVAL remains the attributable count.

### A's five cuts are dead on the second instrument

25.50 MB/cycle. Two independent instruments now agree the five cuts change nothing.
W84's retraction is corroborated. The cuts stay flagged off and A works the transplant
